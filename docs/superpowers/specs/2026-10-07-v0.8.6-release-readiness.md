# MIRA v0.8.6 Release Readiness Design

**Date:** 2026-10-07  
**Status:** Approved in conversation

## Goal

Publish v0.8.6 as the first release that ships the current agent-integration
matrix, proves the installed integrations are healthy, and publishes
reproducible SQLite and PostgreSQL benchmark evidence without overstating what
either backend measures.

## Release contract

- MIRA v0.8.6 supports Codex, Claude Code, Windsurf, Cursor, Claude Desktop,
  Hermes, OpenCode, and Pi Agent through `mira agent install`.
- `mira agent doctor` reports the installed client executable correctly when
  that executable is part of the client contract; Claude Code resolves to the
  `claude` executable.
- Every client installation is idempotent, preserves user-authored
  configuration, and records its actual recall and capture modes.
- PostgreSQL with pgvector is runnable locally through Compose and is exercised
  by integration tests and a disposable, backend-specific benchmark run.
- The public SQLite benchmark remains a standalone report. PostgreSQL receives
  a companion report with its own backend, database version, samples, source
  commit, and model provenance. The site identifies the backend for each
  result instead of comparing both as if they shared one environment.
- Documentation, release notes, site copy, benchmark data, and the runtime
  version all name v0.8.6 and use the same client and benchmark claims.

## Design decisions

### Agent capability declaration

The existing `agentinstall.Client` declaration is the authority for supported
IDs, modes, scope, native skill capability, and executable discovery. Command
code must not hard-code a second executable-name list. A client can have no
required executable when its integration is declarative; doctor then verifies
the generated artifacts and reports its skill-guided mode.

### Installed client verification

For every supported client, tests install into an isolated project, run
`status` and `doctor`, reinstall, and verify that owned files occur once. For
clients available on this workstation (Codex, Claude Code, Hermes, OpenCode,
and Pi), the same project-scoped installation is applied after the test matrix
passes. The installation remains inside the MIRA project and is ignored by
Git.

### PostgreSQL benchmark evidence

The benchmark command accepts a disposable PostgreSQL URL only for databases
ending in `_test`. It must use that URL when `backend=postgres`, construct a
MIRA application with the PostgreSQL repository, and run the same quality and
full-recall flow as SQLite. Component-level cases remain backend-specific:
SQLite reports HNSW and SQL fallback; PostgreSQL reports pgvector-backed full
recall. Reports are never silently merged across backends.

Compose provides a local pgvector service whose database name ends in `_test`.
The release run uses an explicit URL and leaves the service lifecycle visible.

### Publication sequence

1. Implement and verify the contracts in a dirty working tree without
   overwriting existing site design work.
2. Start PostgreSQL if Docker is available; otherwise pause for the user to
   start it.
3. Run core tests, integration tests, release benchmarks, static checks, site
   build, and visual page review.
4. Update v0.8.6 versions, release notes, site release index, and benchmark
   snapshots.
5. Commit the core and site changes separately, push, create the GitHub
   release, attach benchmark reports, and deploy the verified site.

## Risks and limits

- A PostgreSQL report is only representative of the recorded host, image,
  model, and database configuration.
- Skill-guided clients do not gain automatic interception merely by installing
  an MCP server. Their published modes must stay explicit.
- External client hook schemas can change. The release checks the files MIRA
  owns and the locally installed executable where applicable; it does not
  claim to simulate proprietary client internals.
